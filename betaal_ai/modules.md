# AI Backend Modules — Betaal AI

This document details the discrete backend modules, mathematical models, and AI components powering the FastAPI server.

## 1. Core Mathematical Engines (`engine/`)

These purely mathematical engines handle the calculations behind the core "Betaal" experience — interrupting screen time dynamically and managing quotas without relying on ML models.

### `interruption_math.py`
*   **Purpose:** Decides *which* interruption to trigger based on the user's current session.
*   **Logic:** Uses weighted random selection. It does not blindly pick; it factors in the user's `addiction_level`, the time spent in the current app, and the current `Rehab Phase`.
*   **Intensity Curve:** Utilizes a **Sigmoid function** to calculate intensity. The longer a user stays on a distracting app, the steeper the penalty curve becomes, shifting from gentle interruptions (blur screen) to aggressive ones (black screen, reverse scroll).

### `quota_calculator.py`
*   **Purpose:** Calculates the daily allowed screen time (quota) dynamically.
*   **Logic:** Takes the user's historical 7-day average and applies a strict reduction formula depending on the current Rehab Phase:
    *   *Awareness (Phase 1):* 90% of old average.
    *   *Reduction (Phase 2):* 65% of old average.
    *   *Discipline (Phase 3):* 40% of old average.
    *   *Freedom (Phase 4):* 20% of old average.

### `cooldown_calculator.py`
*   **Purpose:** Calculates how long the user must keep the screen locked to earn a "grace period."
*   **Logic:** Linear decay based on the intensity of the *last* interruption. If a user was hit with an 80% intensity interruption, they might need an 8-minute cooldown before the interruptions reset to 0% intensity.

### `rehab_formula.py`
*   **Purpose:** Determines the total length of the rehab program.
*   **Logic:** `duration_days = clamp(addiction_level × 3 × (6 - strictness), 7, 90)`.

## 2. Artificial Intelligence & Machine Learning (`ml/` & `services/chat_service.py`)

### Predictive ML Model (Screen Time Forecasting)
*   **Type:** `RandomForestRegressor` (via `scikit-learn`).
*   **Purpose:** Forecasts how many minutes the user *will* spend on their phone today.
*   **Features Used:** `day_of_week`, `hour`, `past_3_day_avg`, `addiction_level`.
*   **Lifecycle:** The model is trained on a synthetic dataset (`dummy_data_generator.py`) upon server boot-up for the demo, then saved as a `.pkl` file for fast inference (`predict_service.py`).

### Conversational AI (Gemini Pro)
*   **Provider:** Google Gemini API (`gemini-pro`).
*   **Purpose:** Acts as "Betaal", a strict but helpful digital rehab assistant.
*   **Implementation:** `chat_service.py` intercepts the user's message, fetches their latest JSON usage stats, and prepends this as a *System Prompt* so the Gemini API has real-time context on the user's behavior.
*   **Risk Evaluation:** A specific `POST /ai/evaluate` endpoint asks Gemini to ingest the user's weekly JSON and return a structured classification string ("High Risk", "Moderate Risk") and actionable tips.

## 3. External Integrations (`services/youtube_service.py`)

### YouTube Recommendations
*   **Provider:** YouTube Data API v3 (or standard proxy alternative).
*   **Purpose:** Serves positive, productive content to the frontend dashboard.
*   **Logic:** When a user triggers the `POST /youtube/recommend` endpoint, the backend translates the user's current goal (e.g., "focusing on homework") into query keywords. It fetches video IDs, thumbnails, and direct links to render within the Betaal dashboard.

## 4. Usage Aggregation & Monitoring

### `usage_service.py`
*   **Aggregations:** Ingests raw `UsageEvent` objects (start time, end time, app name) and aggregates them into simple daily totals. 
*   **Heat Maps:** Transforms the raw logs into a 2D matrix (Days of the week X Morning/Afternoon/Evening) for rendering visual heatmaps on the Next.js frontend.
*   **Extension Sync:** Receives total browser minutes from the Chrome Extension and deducts it from the same unified daily quota pool as mobile usage.

### `monitor_service.py`
*   **Purpose:** Handles the Multi-User / Parental Linking functionality.
*   **Logic:** Verifies link codes generated by child accounts and binds `child_uid` to `parent_uid` within Firestore. Unlocks the `GET /monitor/{child_id}/stats` route, aggregating the data from the child's `usage_service` to allow a parent/peer to view their dashboard remotely.
